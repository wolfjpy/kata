# M7:投机解码的其它方案(DFlash2、Bonsai 2B drafter、更深的 MTP)和宽验证的代价

日期:2026-10-24 · 全部数据在同一台 Mac mini M6 上实测。

## 1. 问题

现在是 MTP 深度 1、验证宽度 2(25 tok/s)。能不能用更强的 drafter(Kata-2 2B、DFlash2、更深的 MTP 链)再加速?

## 2. 接受率实测(Prism llama.cpp 的 `llama-speculative-simple`,Bonsai-2-27B 为目标模型,贪心)

Prism 自己的 Metal 投机路径很慢(5–9 tok/s,不要看速度),但接受统计有效。"每轮产出的 token 数" = 总解码 token / 验证轮数(每轮 = 已接受 + 1 个额外 token)。

| drafter | 散文(无思考) | 代码(无思考) | 推理(思考模式) |
|---|---|---|---|
| MTP 深度 1 | 1.6–1.64(我们引擎实测) | — | 1.86 |
| MTP 深度 3(链式) | 1.87 | 3.2 | 3.13 |
| **DFlash2**(7 个草稿 token,Q4_K_M) | 2.2 | **5.1** | **5.1** |
| Kata-2 2B(普通草稿模型,4 个草稿 token) | 1.23 | 2.07 | — |

要点:
- **接受率强烈依赖文本的可预测性**:同一个 MTP 链,散文 1.87、代码 3.2。思考模式是可预测的推理文本,默认模式正好落在高接受率一侧。
- **DFlash2 对 Kata 迁移得很好**:`z-lab/Qwen3.8-27B-DFlash2`(1.92B 参数,GGUF Q4_K_M 1.14 GB)是为原版 Qwen3.8-27B 训练的,但在三值量化的 Kata 上代码/推理仍有 5.1 的接受长度(官方 H200 数据:GSM8K 5.46,MTP 链 5.02)。
- **Kata-2 2B 作为草稿模型不值得**:接受长度只有 1.2–2.1,低于 MTP 链;并且每个草稿 token 要读 0.44 GB。
- DFlash2 是块扩散:一次前向产出整个块(8 个 token),所以每个草稿 token 的带宽成本只有 ~0.14 GB(Q4_K_M),远低于逐 token 的草稿模型,但它需要目标模型的隐状态做 KV 注入,因此草稿必须等验证完成,不能在 CPU/ANE 上与验证并行。

## 3. 关键约束:宽验证内核的代价(`tools/bench_gemv2`,ffn_gate 5120→17408,每矩阵)

| 内核 | T(同时验证的 token 数) | 耗时 |
|---|---|---|
| LUT + half2(现用) | 2 | 170–185 µs |
| 同上(2 个 half2 对) | 4 | 296 µs(+60%) |
| 同上 | 6 | 397 µs |
| 同上(每矩阵 4 个 half2 对,NR=2) | 8 | 590–598 µs(**3.2×**) |
| 矩阵单元原型 `k_wide_gemm`(TG 内存 fp16 块 + `matmul2d`,M=16) | 16 | 831 µs |

- 现有的乘加内核随 T 近似线性变慢(ALU 受限),T=8 的验证约 160 ms/轮 → DFlash2 一轮 ~170 ms 产出 5.1 个 token ≈ 30 tok/s,**不比现在的 MTP 深度 1(推理文本 ~29 tok/s)好**。MTP 深度 3 同理(~30 tok/s)。所以在现有内核下,深度 1 确实是最优点,这与之前的估算一致,现在有了数据。
- 矩阵单元原型**数值正确**(最大误差 3e-6,比 half 累加精确得多;权重以精确 fp16 解码)但**慢**:每个 K 块"加载→解码→屏障→matmul2d→屏障"串行,每个 TG 用 20 KB TG 内存 → 每核只能驻留 1 个 TG,没有延迟隐藏;估计每步 ~3.6 µs(预算 ~0.8 µs)。理论上 T=16 的验证可以做到接近带宽(权重只解码一次,乘加在矩阵单元里近乎免费),但需要软件流水、更小的 tile(让每核驻留 2+ 个 TG)、异步拷贝,不是一个小改动。

## 4. 结论与建议

| 方案 | 预期 | 前提 | 建议 |
|---|---|---|---|
| 当前:MTP 深度 1 | 25 tok/s | — | 保持 |
| MTP 深度 3 / 自适应深度 | 推理/代码 ~+0–5%,散文 −20% | 现有内核 | 不做 |
| Bonsai 2B 草稿模型 | 低于 MTP | — | 不做 |
| **DFlash2 + 宽验证** | 推理/代码 ~60 tok/s(估算:草稿 ~9 ms + 宽验证 ~65 ms ≈ 75 ms/5.1 token),散文约持平 | ① 宽验证内核做到 T=8–16 ≲ 1.5× 的 T=2 耗时;② 在 Metal 实现 DFlash2(块扩散 Transformer、双抽头动态卷积、选择器、KV 注入、Q4_K_M 解量化);③ 抽取目标模型若干层的隐状态;④ 块草稿的无损采样 | **唯一能显著提升解码速度的方向,但属于多天、高风险工程**;建议先用 1–2 天把宽验证内核做到目标(这是决策闸门),达标再做 DFlash2 |
| CPU/ANE 做 drafter | — | — | UMA 下带宽共享,草稿 token 的 DRAM 流量与 GPU 争用,只能重叠延迟;DFlash2 又依赖目标隐状态无法并行;ANE 不能原生运行三值权重。不建议 |

## 5. 附带发现:T=1 解码的读取模式上限

`tools/weight_read_probe`:纯读取(不解码、不乘加),原生 28 字节块布局上的小读取(2 字节/1 字节)只有 125–132 GB/s,同样字节数用 16 字节向量读取是 141–142 GB/s(= DRAM 上限)。我们的 GEMV(127–134 GB/s)已经贴在原生布局的读取上限。重排成 16 字节对齐的布局(原设计的 "8 行 × 1024 K 一个 tile,14 条缓存行无填充")理论上可让普通解码 +8–10%(19.8 → ~21.5 tok/s),验证路径同理。

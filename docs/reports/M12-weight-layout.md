# M12:权重布局(16 字节宽读取)——闸门未达到,不实现

日期:2026-10-25 · 对应 CHECKPOINT-003 路线图 M12(原计划:`kata-pack` 生成分平面文件,预期解码 +8–10%)。

## 1. 前提和测量

前提来自 `tools/weight_read_probe`:**不做任何计算,只读**,原生 28 字节块布局上的小读取(2/1/1/2 字节)是 124–132 GB/s,同样字节数用 16 字节向量读取是 141–142 GB/s。ninfer 的分平面权重布局和 Prism CUDA 的 planar 激活布局是同一个思路。

这轮先按"访问宽度"细分(lane 间连续访问,已按实际读取字节数归一化):

| 每 lane 访问宽度 | 带宽 |
|---|---|
| 原生(2/1/1/2 字节) | 124–132 GB/s |
| 4 字节 | 127 |
| 8 字节 | 135 |
| 12 字节(3 个相邻 32 位) | 134–138 |
| 16 字节 | 138–139 |
| 整行 16 字节向量 | 140–142 |

并发现**不需要改文件**:每一行都是 16 字节对齐的(行长 1120/1344/3808 字节),一个"4 个块"(112 字节 = 7 个 16 字节向量)在行内是对齐的。所以可以让 simdgroup 协作地用 16 字节宽读取把 4 行 × 112 字节搬进 TG 内存,再由各 lane 从 TG 内存读小字段——全局读取指令少 16×、零格式改动。

## 2. 原型结果

`docs/probes/gemv_staged_prototype.metal`(`k_gemv_v1s`,软件流水:先发下一个 quad 的全局读取,再计算当前 quad):

| 形状 | 原生读取的 `k_gemv_v1` | 暂存读取的 `k_gemv_v1s` |
|---|---|---|
| ffn_gate/up | 131.4 GB/s | 130.1 |
| ffn_down | 127.4 | 126.0 |
| gdn_qkv | 129.6 | 126.2 |
| lm_head | 134.2 | 134.6 |

**没有提升。** 说明:这个原型的**结果是错的**(最大偏差 ~1e6,修了 TG 数组对齐之后仍然如此,原因没有找到);但指令混合与原版相同(同样的解码、同样的 FMA、读取改成了 TG 内存的小读取),所以耗时仍有代表性。

## 3. 结论

GEMV 里加上解码计算之后,读取宽度不是限制因素:全局读取指令减少 16×、读取模式变成 16 字节连续,速度不变。这与早先的消融一致(去掉解码、去掉激活读取都只有 3–7% 的变化):GEMV 处在**解码 ALU、读取和延迟三者不完全重叠**的平衡点,单独改善任何一项都拿不到收益;纯读取探针的 141 GB/s 不能带过来。T=1 的 GEMV 已经是持续带宽的 89–94%(ffn_gate 92%、ffn_down 89%、qkv 92%、lm_head 94%),剩下的上限 ≤ 8%,想拿到需要同时重构解码和读取的重叠,代价与不确定性都大。

所以 **M12 不实现**(没有写 `kata-pack`,没有改动任何引擎代码或权重文件)。这与 CHECKPOINT-003 里"原生 28 字节块上 8–10% 的读取差距只能靠重排拿回"的判断相反,已更正。

## 4. 随带的改动

- `tools/weight_read_probe` 增加按访问宽度的测量(并修正了读取字节数的归一化)。
- `shaders/layout_probe.metal` 增加 `k_read_w4/8/12/16`。
- 如果以后要重新尝试:更值得做的是 T=1 的 LUT + half2(每字节 3 条 half2 FMA + 1 次 16 字节 LUT 读,替代现在的 1 次转换 + 5 次乘-floor + 5 次 FMA),它同时减少 ALU 指令数,而不是只动读取。

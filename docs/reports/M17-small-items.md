# M17:小项——逐个测量,没有一项达到 1% 的保留线

日期:2026-10-25 · 对应 CHECKPOINT-003 路线图 M17(规则:各自的收益 ≥ 1% 才保留)。结论:**都不实现**,原因和数据如下。

| 项 | 测量/估算 | 结论 |
|---|---|---|
| 主线程 QoS(`QOS_CLASS_USER_INTERACTIVE`),猜测 CPU 采样的 0.1–0.9 ms 抖动是被调度到能效核 | 4 轮交错对照:22.5/22.5、22.6/21.9、21.6/21.9、22.3/22.5 tok/s | 无效果,撤销 |
| 采样 top-K 的 NEON 版本(每次比较 16 个 logit) | 采样耗时 0.2–0.8 → 0.1 ms/周期,输出位级一致;4 轮交错的总耗时 7.01/6.93、6.95/6.96、6.89/6.97、6.90/6.94 s | 端到端在噪声内,撤销(M10 的单遍 top-K 保留) |
| 草稿 + 验证放进同一个命令缓冲区(草稿的 token 由 GPU 直接交给验证,验证的 CPU 编码 ~0.8 ms 与草稿的 GPU 执行重叠) | 估算每周期省 ~1.1 ms(GPU 空闲:编码 0.8 ms + 提交延迟 0.3 ms),约 1.7%;实现需要 `mtpRows`/`verify2` 的异步版本、一个草稿结果缓冲区和 GPU 侧的 token 拷贝 | 低于保留线的价值/复杂度比,推迟 |
| 草稿 lm_head 词表子集(ninfer 的 131072 行) | 省 ~0.9 ms/周期(1.4%);需要按词频的 token 排名,仓库里没有 | 推迟 |
| suffix drafter + 在线成本策略(Strata) | T=2 的验证窗口只有 1 个草稿槽;代码上 MTP 的接受率已经 85%,suffix 只在长匹配时把 65% 提到 95%(重复文本 +3–9%,一般对话 ~0);多 token 草稿需要 T≥3 的验证内核(T=4 比 T=2 贵 60%,M14 的宽内核在 T<6 反而更慢) | 没有宽验证就没有意义,推迟 |

值得记住的数据点:CPU 采样、QoS 这类主机侧的小优化在 62–66 ms 的周期里都淹没在噪声里;真正的剩余时间是 GPU 上的 ~51 ms 验证 GEMV(113 GB/s)和 ~6 ms 草稿(MTP 层 + lm_head 读 0.73 GB)。
